Norwegian Dictionary App

A streamlined, interactive dictionary application designed to facilitate Norwegian language learning through word definitions, example sentences, and a vocabulary game.

Features

Search Functionality: Access word definitions, translations, and example sentences.

Word Game: Practice vocabulary through a matching game with level-based progression and spaced repetition.

CEFR Levels: Filter vocabulary based on CEFR levels for structured language acquisition.

Dynamic UI: Mobile and desktop-compatible layout with adaptive styling.

## Crawlable page builds

`norwegianWords.csv`, `norwegianStories.csv`, `norwegianSounds.csv`, and
`storyQuestions.json` remain the editable source files. Normal local development
does not require a build: the application continues to load those files directly,
so edits appear immediately on a local server.

When VS Code's **Show Preview** serves the repository at
`http://127.0.0.1:3000/`, generated pages use the same root-mounted paths:

- `http://127.0.0.1:3000/word/forgjeves/`
- `http://127.0.0.1:3000/story/bakeriet/`
- `http://127.0.0.1:3000/stories/`

The generated HTML uses directory-relative site bases, so these are the same
files deployed at `/norwegian/word/...`, `/norwegian/story/...`, and
`/norwegian/stories/...` on GitHub Pages. There is no separate local rendering
implementation. Source-data edits still appear immediately in normal app
navigation. A generated URL shows its last captured HTML snapshot; shared CSS
and JavaScript edits load immediately, while captured word/story content is
refreshed by the local page builder or the next GitHub Actions deployment.

Production word and story HTML is generated by a real Chromium browser. The
builder invokes the application's own rendering functions and captures their
output; it does not maintain a smaller or separate implementation of those
pages. A deployment is rejected if page counts, canonicals, shared application
assets, the page manifest, or the sitemap are inconsistent. Representative
pages are also compared pixel-for-pixel with fresh JavaScript renders, followed
by an interaction smoke test.

GitHub Actions runs the full process on every push to `main`. For the workflow to
publish, set **Settings → Pages → Build and deployment → Source** to **GitHub
Actions**. The generated directories remain tracked during the initial
no-downtime migration from branch publishing. After the first successful Actions
deployment has been verified, `word/`, `story/`, `stories/`, `sitemap.xml`, and
`page-manifest.json` can be removed from source control; the workflow recreates
them before every deployment and `.gitignore` prevents accidental recommits.

To reproduce the complete production build locally:

```bash
python3 -m pip install --requirement requirements-pages.txt
python3 -m playwright install chromium
npm run build:pages
```

The build intentionally recaptures every word and story so a change to shared
JavaScript, styling, or application markup cannot leave only part of the static
site stale. It can take substantially longer than the normal local development
loop.
